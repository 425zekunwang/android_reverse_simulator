TOOLBOX

工具箱：本课程涉及的真实项目

这门课讲的每一个技术，背后都有一个真实存在、可以直接下载来用的开源项目。 看懂别人的实现，是最快的学习方式——下面把 32 章里提到的工具全部列出来， 标注了它能解决什么问题、处于技术栈的哪一层、以及和课程哪一章对应。

共 50+ 个项目 按 技术层级 分组 标注 验证状态
⚠️ 关于链接和版本

下面标注「已核实」的项目，其仓库地址与核心特性在本模拟器编写时被实际访问确认过。 标注「待核实」的，是课程中提到但仓库路径可能已变更或未确认的项目—— 请自行搜索确认，不要直接照搬。开源项目演进很快，以官方仓库的当前文档为准。

L1动态插桩 · 观测层

这一层的工具回答一个问题：程序运行时到底发生了什么？

Frida
跨平台动态代码插桩框架。把 JS 引擎注入目标进程，用 JS 写 Hook 逻辑。
已核实 frida.re
对应章节：第 15、16、24 章
frida-gum
Frida 的底层 C 库，提供 Interceptor（inline hook）、Stalker（代码追踪）、 MemoryAccessMonitor、代码生成与重定位等核心能力。想理解 Frida 原理必读。
已核实 github.com/frida/frida-gum
对应章节：第 15 章（Stalker 原理）
frida-ios-dump
iOS 砸壳工具，基于 Frida 从内存 dump 已解密的 Mach-O 并重建二进制。
待核实 仓库地址请搜索确认
对应章节：第 28 章
Dobby
轻量级多平台 inline hook 框架，被 unidbg 用作 hook 后端。
已核实 github.com/jmpews/Dobby
对应章节：第 21 章
xHook
爱奇艺开源的 Android PLT/GOT Hook 框架，用于 hook 导入函数（如 strcmp）。
已核实 github.com/iqiyi/xHook
对应章节：第 15、21 章

L2模拟执行 · 黑盒调用层

这一层回答：能不能不启动 App，直接把 so 里的函数跑起来？这是算法还原最高效的落地方式。

Unicorn
基于 QEMU 的 CPU 模拟器框架。只模拟 CPU，不模拟系统，所以轻量、可嵌入。
已核实 github.com/unicorn-engine/unicorn
对应章节：第 21 章
Capstone
反汇编框架。把机器码翻译成汇编文本，支持 ARM/ARM64/x86 等多架构。
已核实 github.com/capstone-engine/capstone
对应章节：第 21 章
Keystone
汇编框架。把汇编文本翻译成机器码，与 Capstone 互为逆运算。
已核实 github.com/keystone-engine/keystone
对应章节：第 21 章
unidbg ★
本课程算法还原的主力工具。一体化 Android native 库模拟器：模拟 JNI Invocation API （可调用 JNI_OnLoad）、支持 JavaVM/JNIEnv、模拟 syscall 指令、ARM32/ARM64、 inline hook（Dobby）、import hook（xHook）、指令 trace、内存读写 trace， 并支持 dynarmic / Apple M1 hypervisor / Linux KVM 多种加速后端。 近期还加入了 MCP 支持，可让 AI 辅助调试。
已核实 github.com/zhkl0228/unidbg
对应章节：第 21、22、23 章
AndroidNativeEmu
Python 实现的 Android native 库模拟器，基于 Unicorn + Keystone。 JNI Invocation API 模拟、malloc/memcpy 模拟、syscall（SVC #0）模拟、 通过符号表 hook，JavaVM / JNIEnv / hooked 函数全部由 Python 处理。 比 unidbg 轻量，适合快速验证想法。
已核实 github.com/AeonLucid/AndroidNativeEmu
对应章节：第 21 章

L3脱壳 · ART 虚拟机层

这一层回答：怎么把壳藏起来的真 dex 和真代码挖出来？

FART ★
ART 环境下基于主动调用的自动化脱壳方案。基于 Android 6.0 实现，理论上可移植到任何 ART 系统。 核心是遍历所有方法并主动调用（Active Call），强制触发 ART 的解密/回填逻辑， 再 dump dex 与 code item。脱壳产物在 /sdcard/fart/<包名>/， 完成时 logcat 中 tag 为 ActivityThread 的日志会打印 fart run over。 作者同时提供了 Frida 版 FART，可精确到对某个类甚至某个函数的 CodeItem dump。
已核实 github.com/hanbinglengyue/FART
对应章节：第 16、24、26 章
fdex2
另一条经典脱壳路线，通过 Hook DexFile 相关方法在内存中 dump dex。 高版本 Android 需要适配（ART 内部结构变化）。
待核实 仓库地址请搜索确认
对应章节：第 24 章
jadx
Dex 转 Java 反编译器。FART 脱出的 dex 常因结构损坏被拒绝，需要定制版放宽校验。
已核实 github.com/skylot/jadx
对应章节：第 24 章
AOSP
Android Open Source Project。第 18 章要定制 ART、第 26 章要移植 FART、第 30 章要编译模拟器， 都从这里拿源码。
已核实 source.android.com
对应章节：第 18、26、30 章

L4混淆 · 编译器层

这一层回答：对手是怎么把代码变得看不懂的？以及怎么变回去？

Obfuscator-LLVM (OLLVM) ★
本课程第 19 章的主角。基于 LLVM 的开源代码混淆器，通过自定义 Pass 在编译期改写 IR。 官方 wiki 明确的三个混淆选项：-mllvm -sub（指令替换）、 -mllvm -bcf（虚假控制流）、-mllvm -fla（控制流平坦化）， 另有函数注解功能控制混淆范围。最新版本基于 LLVM 4.0。
注意 字符串加密不是 OLLVM 官方特性，是衍生版本添加的
已核实 github.com/obfuscator-llvm/obfuscator
对应章节：第 19、22、23 章
LLVM
模块化编译器框架。理解 Pass 机制（ModulePass / FunctionPass / BasicBlockPass / LoopPass） 是读懂 OLLVM 源码的前提。
已核实 llvm.org
对应章节：第 19 章
D-810
IDA Pro 插件，用于反混淆 OLLVM 保护的代码（识别分发器、追踪状态变量）。
待核实 作者 GuideM，仓库路径可能已变更
对应章节：第 19 章
HexRaysDeob
IDA Hex-Rays 反编译器插件，用来自动化还原 OLLVM 混淆。
待核实 仓库地址请搜索确认
对应章节：第 19 章
ADVMP
开源 VMP（虚拟机保护）实现。课程用它作为"从开源实现理解 VMP 内部机制"的抓手。
待核实 仓库地址请搜索确认
对应章节：第 20 章
OpenSSL
第 23 章要手动编译它（./Configure android-arm64）得到带调试符号的密码学库， 用它编译对照 so，与目标 so 做指令特征比对。
已核实 github.com/openssl/openssl
对应章节：第 23 章

L5内核与虚拟化 · 对抗层

这一层回答：怎么把观测点放到对手看不见的地方？

eBPF
Linux 内核中安全运行沙箱程序的虚拟机。用户态提交字节码 → 内核验证器静态检查 → JIT 编译 → 挂到 kprobe/uprobe/tracepoint/XDP 等钩子点执行 → 通过 BPF Maps 与用户态通信。 运行在内核态，比用户态 Frida 更难被检测。
已核实 ebpf.io
安卓限制 受内核版本与厂商裁剪限制，通常需 root
对应章节：第 25 章
BCC / bpftrace / libbpf
eBPF 的三种主流工具链：BCC（Python 开发快）、bpftrace（类 awk 脚本，适合快速排查）、 libbpf + CO-RE（Compile Once – Run Everywhere，现代推荐）。
已核实 github.com/iovisor/bcc · bpftrace · libbpf
对应章节：第 25 章
Hyperpwn
基于 Hypervisor（ARM EL2 虚拟化扩展）的 Android 调试工具。把目标系统跑在虚拟机里， 从 EL2 层做内存断点与指令追踪。因为用 stage-2 页表做访问控制而不修改 guest 内存， 反调试手段完全无法察觉——这是当前调试对抗的天花板。
待核实 仓库地址请搜索确认
对应章节：第 20、27 章
0r0env
课程作者提供的整套定制调试环境（定制 ROM / 内核），把内核级对抗能力打包成开箱即用。
待核实 以作者发布为准
对应章节：第 27 章
Magisk
Android Root 方案 + 模块化框架。核心是修改 boot 镜像在 init 早期注入， 通过 overlayfs / magic mount 实现 systemless（不改系统分区）的模块挂载， 可以随时干净卸载。Zygisk 提供 Zygote 注入，DenyList 用于隐藏 root。
已核实 github.com/topjohnwu/Magisk
对应章节：第 32 章

L6虚拟化与容器化 · 基础设施层

这一层回答：怎么造一个可控、可伪装、可规模化的运行环境？

QEMU
通用开源模拟器与虚拟机。课程用它讲虚拟化原理、网络模式（NAT/bridge/host-only）、 以及编译调试 Linux 内核。
已核实 qemu.org
对应章节：第 29 章
Waydroid ★
在 Linux 上用容器跑完整 Android 系统的知名方案。官方描述： "uses a container-based approach to boot a full Android system on a regular GNU/Linux system"， 使用 Linux namespaces（user, pid, uts, net, mount, ipc）做隔离， 容器内的 Android 可直接访问所需硬件——这是与模拟器的关键区别，性能接近原生。 系统镜像基于 LineageOS，当前基于 Android 13。
已核实 github.com/waydroid/waydroid
对应章节：第 32 章
Cuttlefish ★
Google 官方的可配置 Android 虚拟设备，面向本地 Linux x86/arm64 与 Google Compute Engine 云端实例， 而非物理硬件。它是理解现代云手机/云测设备的关键——很多云手机方案本质就是它或其变体。 依赖 KVM，通过 Debian 包（cuttlefish-base / -user / -orchestration）安装。
已核实 github.com/google/android-cuttlefish
对应章节：第 30、32 章
KVM
Linux 内核的硬件虚拟化接口，通过 /dev/kvm 字符设备 + ioctl （KVM_CREATE_VM / KVM_CREATE_VCPU / KVM_RUN）暴露给用户态。 是 QEMU、Cuttlefish、crosvm 等共同依赖的底座。
已核实 linux-kvm.org
对应章节：第 32 章
Docker
容器化的事实标准。课程通过"手写一个迷你 Docker"来证明它不过是 namespaces + cgroup + rootfs + capabilities 的封装，不是黑魔法。
已核实 docker.com
对应章节：第 31 章
debootstrap
Debian/Ubuntu 的引导工具，可在指定目录构建最小根文件系统。 课程用它手工构建 Docker 三种网络模式的实验环境。
已核实 wiki.debian.org/Debootstrap
对应章节：第 31 章
remote_android
课程作者的云端安卓项目——把前 17 章的技术（容器化、虚拟化、图形加速、反检测） 整合落地成可远程访问的安卓运行环境。
待核实 以作者发布为准
对应章节：第 32 章

L72w 计划基础模块 · 观测与协议层（第 19–25 章）

这一组是后补的 2w 计划班内容里提到的工具。它们解决的是同一个问题： 在动手分析之前，你怎么先看得见？——JNI 怎么绑定、脚本怎么自动化、包怎么抓到手、算法怎么自己招供。

objection
基于 Frida 的免脚本运行时操作台，支持 iOS 与 Android。 官方 README 列出的能力包括：检查并操作容器文件系统、绕过 SSL pinning、dump keychain、 内存 dump 与 patch、堆对象探查等。安装就是 pip3 install objection。
要记住的取舍：它底层就是 Frida，所以它的特征暴露面也是 Frida 的——用它可以省掉写脚本，但省不掉去特征。
已核实 github.com/sensepost/objection
对应章节：第 10 章（Frida 自动化与去特征）
r0capture
作者自述为「安卓应用层抓包通杀脚本」。它的思路是不在两端的证书上较劲， 而是在 socket / SSL 层直接拿明文，因此 README 声称无需关心证书校验或绑定， 并覆盖 Http / WebSocket / Ftp / Xmpp / Imap / Smtp / Protobuf 等及其 SSL 版本， 以及 HttpURLConnection / OkHttp / Retrofit / Volley 等框架。
README 明确写了两条前提：① 仅限安卓，禁止使用模拟器；② 推荐按 Frida 版本与安卓版本搭配（README 给了对应表）。
上面是项目自述口径，不是本页的实测结论——它失效的情况一定存在（例如不走标准 TLS 栈的 native 直连）。
已核实 github.com/r0ysue/r0capture
对应章节：第 10、12 章
r0tracer
作者自述为「安卓 Java 层多功能追踪脚本」，别名「精简版 objection + Wallbreaker」。 支持按黑白名单批量追踪类的所有方法、命中后打印域值/参数/调用栈/返回值、文本日志便于搜索， 以及针对加壳应用找不到类时切换 ClassLoader。README 也提到 hookALL() 模式 「小应用可用，大应用扛不住」——这是一个很实在的自我限制说明。
已核实 github.com/r0ysue/r0tracer
对应章节：第 10、13 章
hluda（去特征 Frida 分支）
社区对 Frida 源码做深度改造后构建的分支，目标是抹掉常规特征（特征字符串、模块名、 默认端口行为、线程特征等），从而绕过针对标准 Frida 的探测。
为什么标「待核实」：它没有唯一的上游官方仓库，社区存在多个来源与版本 （例如各类“魔改版 frida-server”分发），命名也不统一。不要照抄某个 URL 或版本号—— 常见做法是自己按第 10 章讲的思路改源码后编译，或确认你所选分支的当前维护状态。
待核实 无单一上游，请自行确认来源与版本
对应章节：第 10 章
LSPosed ★
官方 README 定位为「一个 Riru / Zygisk 模块，提供与原生 Xposed 一致的 API 的 ART Hook 框架」， 底层使用 LSPlant 作为 hook 框架。相比原始 Xposed，它是当前 Android 上更可用的选择。
安装链路（README 原文口径）：Magisk v24+ →（Riru 分支需 Riru）→ 在 Magisk 里安装 LSPosed → 重启。
注意作用域（scope）：模块只对你在管理器里勾选的 App 生效——这是它与 Frida「注入哪个进程就影响哪个进程」最大的操作差异。
待核实 README 给出的支持版本快照会滞后于实际 release，请以仓库当前 release 说明为准
已核实 github.com/LSPosed/LSPosed
对应章节：第 11 章（Xposed / LSPosed 开发指南）
Xposed（原版）
模块化 Hook 框架的鼻祖，"不修改 APK 就能改系统与 App 行为"这个思路由它定义， 也是 LSPosed 兼容的那套 API 的来源。原版对高版本 Android 的支持早已停止， 现在学习时应把它当作API 规范与历史参照，实际动手用 LSPosed。
待核实 原版仓库与兼容性状态请自行确认
对应章节：第 11 章
mitmproxy
官方定位「An interactive TLS-capable intercepting HTTP proxy for penetration testers and software developers」。 它相对 Charles / Fiddler 的关键差异是可脚本化（Python 插件直接改写请求响应）—— 在遇到混淆型案例、需要按条件批量改写或自动打标时，这一点是决定性的。
已核实 github.com/mitmproxy/mitmproxy
对应章节：第 12 章
Charles
老牌 HTTP 代理 / 监视器 / 反向代理，官方自述可查看本机与互联网之间的全部 HTTP 与 SSL/HTTPS 流量 （含请求、响应与 Header）。图形界面友好、上手快，是很多人第一个抓包工具。
局限：不可脚本化（对比 mitmproxy），复杂对抗场景下不够灵活。
已核实 charlesproxy.com
对应章节：第 12 章
Reqable
官方自述「Reqable = Fiddler + Charles + Postman」：MITM 代理 + API 调试一体化， 单个端口适配 HTTP/HTTPS/SOCKS4/SOCKS5，支持 HTTP/2、TLS 1.1–1.3、 Python 脚本改写、SSL Bypass、移动端协同与 MCP Server。
为什么值得在这里列出来：它把「抓包 + 改包 + 调接口」放在同一个工具里， 做协议分析时可以减少在多个工具间来回搬数据。
已核实 reqable.com
对应章节：第 12 章
AppMon（APPMON）
官方 README 自述为「an automated framework for monitoring and tampering system API calls of native macOS, iOS and android apps」， 基于 Frida。它的关注点不是某个具体算法，而是应用调用了哪些系统 API—— 这正是第 13 章讲的"把观测点插在框架层，一次覆盖一大批样本"的思路来源。
提醒：课程里提到的 APPMON 与这个项目是否同一个实现，请自行确认； 本页只保证这个仓库存在且定位吻合，不代课程下结论。
已核实 github.com/dpnishant/appmon
对应章节：第 13 章（自吐沙箱与算法自监控）

L81w 计划入门模块 · 格式、审计与改包层（第 26–32 章）

这一组是后补的 1w 计划班内容里提到的工具。它们回答的是更靠前的问题： 文件长什么样、包能不能改、App 自己有哪些缺陷。

apktool ★
官方描述「A tool for reverse engineering Android apk files」。它做两件事： 把 APK 解码成可读的资源 + smali，以及把改过的 smali/资源回编译成 APK。
它是"改包"这条路的起点——但它只负责"解包与回编译"，不负责签名： 回编译出来的包必须自己重新签名才能安装，而签名一变就会触发目标 App 的签名校验（第 8 章）。
已核实 github.com/iBotPeaches/Apktool
Apache-2.0 · Java · 创建于 2012-03 · 最近推送 2026-09
对应章节：第 2 章（Smali 与重打包）、第 3 章（APK 结构）
smali / baksmali
dex 字节码的汇编器 / 反汇编器：baksmali 把 dex 反汇编成 Smali 文本， smali 反过来把 Smali 汇编回 dex。apktool 内部的 smali 处理就是靠它。
它比 jadx 更适合"改"：jadx 面向"读"，baksmali/smali 面向"读+写"这一对往返。 另外在 dex 结构受损时，baksmali 的容忍度通常比 jadx 高（第 16、24 章都提到过这一点）。
已核实 github.com/google/smali
现已迁到 google 组织下（原为 JesusFreke/smali）；仓库未提供标准 SPDX 许可标识，采用前请自行确认许可
对应章节：第 2 章
LIEF
官方描述「Library to Instrument Executable Formats (C++, Python, Rust)」。 能把 ELF / PE / Mach-O 解析成结构化对象、并修改后写回——正好对应第 3 章要拆的那四张表 （头 / 程序头 / 节表 / 符号表）。和 pyelftools 的区别是它能"改"，不只是"读"。
已核实 github.com/lief-project/LIEF
Apache-2.0 · C++ · 创建于 2017-03 · 最近推送 2026-09
对应章节：第 3 章
pyelftools
官方描述「Parsing ELF and DWARF in Python」。纯 Python、零依赖的 ELF 解析库， 非常适合"边学边验证"：你在第 3 章学一个字段，就用它读一个真实 so 出来的值对照一下。
已核实 github.com/eliben/pyelftools
Python · 创建于 2013-06 · 最近推送 2026-07
对应章节：第 3 章
Androguard

MobSF ★
官方描述「Mobile Security Framework — an automated, all-in-one mobile application (Android/iOS/Windows) pen-testing, malware analysis and security assessment framework」。 官方 README 给了 Docker 起服务的方式（拉镜像 → 映射 8000 端口 → 浏览器访问，默认账号 mobsf/mobsf，凭据请以官方当期说明为准）。

Drozer
官方描述「The Leading Security Assessment Framework for Android」。 它的独特价值是以"攻击者 App"的身份在真机上实际调用你的组件—— 能发现静态扫描发现不了的问题（比如一个导出的 Provider 是不是真的能读到别人的数据）。
注意两点：① 它几经易主（现在在 WithSecureLabs 组织下），发布形态、Python 版本与命令语法都变过，不要照抄老教程； ② 它测的是组件暴露面，不是业务逻辑漏洞。

对应章节：第 6 章
AndProxy
官方描述「Android library for intercepting Binder transactions and system calls via GOT hook and seccomp, enabling dynamic modification of IPC data and syscall behavior」。
它是第 1 章那条判断的工程化兑现：Binder 的物理落点是对 /dev/binder 做 ioctl—— 所以用 GOT Hook 劫持 libbinder.so 里的 ioctl，就能拦下全部 Binder 事务，并解析出服务名与方法名。
它同时也印证了"底层手段总带版本枷锁"：仅支持 ARM64，且需要内核 ≥ 5.10（Seccomp 用户态通知）。
已核实 github.com/ggggmllll/AndProxyDemo
GPL-2.0 · C++ · 创建于 2026-03 · 最近推送 2026-04
对应章节：第 1 章（本章案例）

MY我的产出

这里放的是你自己做出来的东西，不是讲义。每通过一个动手实验室， 系统会把你的结论与正确答案整理成一份可复用的产出物——学完 32 章，你会攒下一套真正能用的工具集。

GL名词速查

按技术层级排列的术语索引。带 ★ 的是贯穿全课的核心概念。

DBI
Dynamic Binary Instrumentation，动态二进制插桩。运行时插入代码观测/修改程序行为。
ART ★
Android Runtime，Android 5.0 起取代 Dalvik。把 dex 编译为机器码执行，保留 Java 反射能力。第 18 章要直接改它的源码。
JNIEnv
JNI 环境指针，Native 代码调用 Java 层的唯一入口。每线程一份。
RegisterNatives
JNI 动态注册接口。加固常用它让函数地址飘忽不定——第 18 章的定制 ART 就针对它。
Inline Hook
在函数入口写入跳转指令劫持执行流。需可写内存权限与指令重定位能力。
基本块 ★
Basic Block。只有一个入口一个出口、内部无分支的指令序列。控制流分析与 Trace 的基本单位。
不透明谓词 ★
Opaque Predicate。结果恒定但静态难以判定的条件表达式，虚假控制流的核心构件。
控制流平坦化 ★
把结构化控制流改写为由状态变量驱动的 switch 分发器。OLLVM 的 -fla。
魔数 / 常量表 ★
算法中固定的特征数据（MD5 的 IV、AES 的 S 盒、RC4 的 S 盒）。算法还原的主要突破口。
补环境 ★
模拟执行时手工补齐 JNI 环境与系统调用。unidbg / AndroidNativeEmu 要解决的核心问题。
抽取壳 ★
把 dex 中方法体的 code_item 抽走，运行时才回填。所以普通内存 dump 拿到的是空方法。
主动调用 ★
Active Call。FART 的核心——遍历所有方法逐个调用，强制触发解密/回填。
VMP ★
Virtual Machine Protect。把原始指令翻译成自定义字节码，由内置解释器执行，使静态反编译失效。
EL2 ★
ARM 的 Exception Level 2，Hypervisor 运行层级。比内核（EL1）更底层，guest 不可见。
Stage-2 页表 ★
ARM 虚拟化的第二级地址翻译（Guest 物理地址 → 真实物理地址）。Hypervisor 做内存隔离与内存断点的硬件基础。
GKI
Generic Kernel Image。Google 为统一安卓内核碎片化推出的方案：通用内核 + 厂商可加载模块，靠稳定的 KMI 接口协作。
namespace ★
Linux 资源隔离机制（pid/net/mnt/uts/ipc/user/cgroup）。容器隔离的基石。
cgroup ★
Linux 资源限制机制。v2 采用统一层次结构，控制器含 cpu/memory/pids/io。
容器 ≠ 虚拟机 ★
容器共享宿主内核（无硬件虚拟化，开销极小，隔离弱）；虚拟机有独立内核（隔离强，开销大）。
binfmt_misc
Linux 内核功能，让内核把任意格式二进制交给指定解释器执行。配合 qemu-user-static 实现跨架构运行。
FairPlay
Apple 的 DRM。App Store 应用代码段加密，运行时由内核解密到内存——这是 iOS 砸壳存在的原因。
SSL Pinning
证书绑定。App 内置服务端证书/公钥并校验，使中间人抓包失败。
SVC
ARM 的 Supervisor Call 指令。App 直接内联 SVC 可绕过 libc，使基于 libc Hook 的监控失效。
四大组件 ★
Activity（界面）/ Service（无界面后台）/ BroadcastReceiver（接收广播）/ ContentProvider（跨进程数据共享）。必须在清单里显式声明；系统只认识组件，不认识你的业务逻辑。第 1 章。
组件导出 exported ★
决定"别的 App 能不能唤起这个组件"。历史规则是"带 intent-filter 就默认导出"；Android 12 起带 intent-filter 的组件必须显式声明。它同时是攻击面与逆向入口。第 1、4 章。
ContentProvider 创建时机
它的 onCreate 早于 Application.onCreate——系统要先装好"对外提供的能力"，才认为进程准备好了。加固与 SDK 自动初始化常用它抢最早时机。第 1 章。
Handler / Looper / MessageQueue ★
安卓的消息循环模型。每个线程最多一个 Looper；消息按 when（时间戳）排序而非入队顺序；post(Runnable) 与 sendMessage 走同一条路。主线程被卡住 = 某条消息执行太久 = ANR。第 1 章。
Binder ★
安卓的跨进程通信机制。物理落点是对 /dev/binder 做 ioctl（所以基于文件 syscall 的监控看不到它）；调用方 UID/PID 由内核填入、不可伪造；只做一次数据拷贝。第 1 章。
AIDL
接口定义语言。生成 Stub（服务端）与 Proxy（客户端），把跨进程调用封装成看起来像普通方法调用的形式。asInterface 是分叉点：同进程返回本地对象（不走 Binder），跨进程才走 transact。第 1 章。
Smali ★
Dalvik/ART 字节码的可读文本形式。寄存器式（.registers/.locals，参数寄存器 p0… 在编号末尾），五行 invoke 按调用类型区分，返回值必须紧跟 move-result*。第 2 章。
dex vs jar
Android 类加载器只认 dex，不认 JVM 字节码。所以"能被安卓动态加载的 jar"实质是一个内含 classes.dex 的 zip。第 1 章。
dex 索引区
string_ids / type_ids / proto_ids / field_ids / method_ids / class_defs。去重 + 定长寻址是它存在的理由；抽取壳抽走的正是 class_defs 指向的 code_item 里的 insns。第 3 章。
段 vs 节 ★
ELF 里两套视角：程序头（段）给加载器看，决定怎么映射进内存；节表（节）给分析者看，是 .text/.rodata 这套命名。p_memsz > p_filesz 的那部分就是 .bss 的来源。第 3 章。
分区存储 ★
Scoped Storage。Android 10 引入（可用 requestLegacyExternalStorage 临时退回），Android 11 起强制。要访问共享目录须走 MediaStore 或申请「所有文件访问权限」。具体分界以官方文档为准。第 1 章。
RSA ★
非对称加密。公钥本来就是公开的——这是它与对称/摘要最大的不同。方向容易搞反：公钥加密+私钥解密（保密）vs 私钥签名+公钥验签（防篡改）。客户端几乎只能拿到公钥。第 6 章。
填充 padding（RSA）
PKCS#1 v1.5（同明文同公钥两次加密密文相同）vs OAEP（带随机数，两次密文不同）。"看到 RSA 却复现不出结果"的头号原因。第 6 章。
SPKI
Subject Public Key Info，证书/密钥文件里公钥的标准编码结构。从证书里提取公钥，本质上就是解析到这一段。第 6 章。
MCP（Model Context Protocol）
把工具能力标准化暴露给大模型的协议。与"把代码粘进聊天框"的本质区别是模型可以主动索取信息（按需取某个函数的伪代码、查交叉引用）。第 7 章。

  1. 学完一章，就来这里点开对应的仓库。看它的 README、看它的 issue、看它的源码结构—— 真实项目的复杂度会告诉你"课上讲的简化模型"和"工程现实"的差距在哪。
  2. 不要只看不跑。clone 下来编译一次，比读十篇文章有用。unidbg 和 FART 尤其值得亲手跑通。
  3. 注意时效。这个领域演进很快，仓库的当前状态可能已经超出课程录制时的内容。
