CHAPTER 15

Frida 高级逆向

这是整门课的地基。你要在这里建立的第一个、也是最重要的分界线是： Hook Java 层和 Hook Native 层是两条完全不同的技术路径， 它们的原理、工具、能解决的问题、以及失败时的排查方向，全都不一样。 建立不了这条分界线，后面 17 章你会一直在"为什么我 hook 不到"里打转。

核心问题：怎么让程序按我的意志执行？ 关键工具：Frida / Interceptor / Stalker 对手：OLLVM 混淆

15.1先建立直觉：Hook 到底是什么

直觉模型 · 电话总机

想象你在一家公司里，所有打给"财务部"的电话都要经过总机。 现在你想知道老板什么时候给财务部打电话、说了什么、财务部回了什么。

你有两个办法：

  • 办法 A（改分机号表）：你在总机的号码簿上把"财务部"改成你自己的分机。 电话来了你先接，记录完再转给真财务部。—— 这是 Hook Java 层。
  • 办法 B（在电话线上并联一个监听器）：你不改号码簿，而是在物理线路上接一个设备， 任何经过这条线的语音你都听得到。—— 这是 Hook Native 层。

两者都能"截获调用"，但它们的作用位置、能找到的目标、 被发现的难度完全不同。这就是为什么你必须先分清它们。

那么，Frida 在这张图里扮演什么角色？

Frida 的角色是：它同时提供了办法 A 和办法 B 两套 API，而且都只需要写 JavaScript。

维度Hook Java 层Hook Native 层
Frida APIJava.perform / Java.useInterceptor.attach
作用对象Dex 里的方法（Java/Kotlin 编译产物）so 库里的机器码函数
依赖什么ART 虚拟机的 Java 反射机制CPU 层面的指令改写
能找到的目标只要方法存在，就能被 use 到需要拿到函数地址（导出符号 / 基址+偏移）
典型失败原因类加载器不对、方法被内联、方法被抽走地址算错、so 还没加载、函数被混淆改名
被检测难度较容易（查调用栈、查 Method 结构）较难（需要扫内存特征）
🔑 记住这条分界线的判断方法

当你 hook 不到一个方法时，先问自己一个问题： 这个方法是写在 Java 代码里的，还是写在 so 里的？
如果是 Java 代码 → 用 Java.use，失败就往「类加载器」「方法内联」方向查。
如果是 so 里的函数 → 用 Interceptor.attach，失败就往「地址」「so 加载时机」方向查。
90% 的新手卡住，是因为拿错了工具去查错了方向。

15.2Hook Java 层：从一行代码看懂全过程

先看一段最经典的 Frida Java Hook 脚本。别急着背，我们把它拆成 5 步逐步执行， 你会看到 ART 内部到底发生了什么。

三个必须理解的细节

细节 1：为什么必须有 Java.perform？

因为 ART 虚拟机不是一开始就准备好的。App 启动时，VM 还在初始化，类还没加载。 如果你在 VM 就绪前调用 Java.use，就会拿到一个空的、不可用的环境。

Java.perform(fn) 的语义是："等 VM 就绪，并且把我这段代码挂到 VM 的线程上执行"。 它保证了两件事：VM 已启动、当前线程已 attach 到 VM。

⚠️ 常见误解

很多人以为 Java.perform 只是"延迟一下"。 不是。它是线程 attach——Frida 注入的线程默认不是 Java 线程， 没有 JNIEnv，根本没法调用 Java API。Java.perform 帮你完成了 attach 和 detach 的配对管理。

细节 2：Java.use 拿到的到底是什么？

它返回的是一个包装器（wrapper），不是原始的 Class 对象。这个包装器会拦截你对它的所有调用。

你想做的事
var C = Java.use('com.a.b.C');
C.f.overload('java.lang.String')
   .implementation = function (s) {
  return this.f(s);
};
Frida 实际做的事
  1. 找到目标 Class 的 jclass
  2. 反射出方法签名 (Ljava/lang/String;)V
  3. 把原方法标记为 native
  4. 把自己的 C 函数注册进去
  5. 调用时进你的 JS，this.f(s) 再调回原实现
🔥 关键结论：为什么 overload 不能省

Java 允许方法重载——同一个方法名可以有多个不同参数签名的版本。 当你写 C.f 时，ART 不知道你要 hook 哪个。Frida 会直接报错 Error: f(): has more than one overload。 overload() 就是在告诉 Frida：我要的是参数类型为 String 的那一个。

细节 3：this.f(s) 为什么不会无限递归？

这是初学者最容易困惑的地方："我把 f 换成了我的函数，然后在里面又调用 this.f， 这不就是自己调自己吗？"

Frida 在设置 implementation 时，会把原始方法保存起来， 并让包装器上的 this.f 指向那个原始实现（而不是包装后的）。 所以你的调用会落到真正的 Java 实现上。

那如果我不想调用原方法，想直接返回我自己的值呢？

完全可以，而且这是最常用的"绕过校验"手法：

Java.use('com.a.b.Sign').check.overload('java.lang.String')
  .implementation = function (input) {
    console.log('[!] check() 被调用，输入 =', input);
    return true;          // 直接返回 true，根本不执行原逻辑
  };

这种写法叫 "直接替换"。它的优点是快、稳、不受原逻辑影响； 缺点是如果原方法有副作用（比如初始化了某个字段），你不调用就会漏掉， 后续代码可能崩溃。所以能调原方法就调原方法，只在确实要改变返回值时才直接返回。

15.3Hook Native 层：为什么地址是核心问题

Native Hook 的思路完全不同。它不经过 ART，直接在机器码层面动手。

直觉模型 · 修改黑板上的字

想象函数是一块写在黑板上的指令清单，学生（CPU）从头往下读。
Interceptor.attach 做的事是：在清单开头贴一张便签，写着"先跳到讲台（你的 JS 函数）， 讲完再回来接着读"。

这就是 Inline Hook 的本质。它需要三个东西：

  1. 目标函数的地址——你总得知道便签贴在哪块黑板上
  2. 能写内存的权限——黑板上原本是只读的，得先改成可写
  3. 保存被覆盖的那几条指令——回来时要能接上

三种拿到函数地址的姿势

方式代码适用场景坑
导出符号 Module.getExportByName('libx.so','f') 函数是 JNIEXPORT 导出的 混淆后符号名可能被抹掉
模块基址 + 偏移 Module.findBaseAddress('libx.so').add(0x1234) 静态分析拿到了偏移 偏移随版本变化；Thumb 要 +1
运行时查找 Module.enumerateExports() / 扫描特征 符号被改了名，但还在 性能开销大

必须搞清楚的 onEnter / onLeave

onEnter — 函数刚进入，还没执行
  • 能读到输入参数（args[0], args[1]...）
  • 能改参数：args[0] = ptr('...')
  • 读不到返回值（还没产生）
  • 可以用 this.xxx = v 存东西给 onLeave 用
onLeave — 函数执行完，即将返回
  • 能读到返回值：retval
  • 能改返回值：retval.replace(...)
  • 能读到 onEnter 里存的状态
  • 读不到参数（除非 onEnter 时存了）
⚠️ retval.replace() 的经典陷阱

如果你想改一个返回 jstring 的函数，写 retval.replace(ptr('0x0')) 是对的；但如果写 retval = ptr('0x0') 完全无效——那只是改了个 JS 局部变量。这是新手第一大坑。

15.4OLLVM 登场：为什么静态分析会失效

到目前为止一切顺利。但当 App 用 OLLVM 保护关键函数后，你会发现：IDA 里打开那个函数，什么都看不懂了。

OLLVM 有四大杀手锏。我们用同一段逻辑，看看它被每种手段改造后的样子。

原始逻辑（很简单）
int check(int x) {
    if (x == 0x1234) {
        return 1;        // 通过
    }
    return 0;            // 拒绝
}

四大手段逐个拆解

① 字符串加密（String Encryption）—— 让常量在内存里也看不见

做了什么：把代码里的字符串常量（比如 API 地址、密钥、错误提示） 替换成一段解密代码 + 密文。原始字符串在 so 文件里根本不存在， 只有运行时才在栈上解密出来。

混淆前：

strcmp(input, "secret_key")

so 文件里能搜到：

strings libx.so | grep secret
→ secret_key     ← 一眼就看到

混淆后：

char buf[16];
decrypt(buf, "\x3a\x7f\x21...", 10);
strcmp(input, buf);

so 文件里搜不到明文，但：

// 运行时在 decrypt 返回处
// 下一个断点，直接读 buf
✅ 破法

静态搜不到就动态抓。Hook 字符串比较函数 （strcmp/strncmp/memcmp）或解密函数， 在它返回的那一刻把明文 dump 出来。这类脚本是 Frida 最常用的"起手式"。

② 控制流平坦化（Control Flow Flattening，-fla）—— 把 if/else 打散成状态机

做了什么：把原本"从上到下、带分支"的控制流， 改写成一个巨大的 switch 循环。所有基本块变成 case， 用一个人工变量（state）来决定下一步跳哪。

// 混淆前：控制流清晰
if (x == 0x1234) return 1;
return 0;

// 混淆后：一个 switch 分发器 + 状态变量
int state = 0x8A3F21;          // 初始状态是随机数
while (1) {
    switch (state) {
    case 0x8A3F21:
        state = (x == 0x1234) ? 0x11B7C2 : 0x44DE09;
        break;
    case 0x11B7C2:
        ret = 1; state = 0xFFFFFF;   // 出口
        break;
    case 0x44DE09:
        ret = 0; state = 0xFFFFFF;
        break;
    }
    if (state == 0xFFFFFF) break;
}
为什么这让 IDA 崩溃

IDA 的 F5 反编译依赖识别控制流结构（if、循环、switch）。 平坦化之后，所有代码都变成了"一个 switch 的 case"， 反编译器无法判断真实的执行顺序，产出的伪代码就成了一坨 while(1) switch(state) 里塞满赋值语句的东西。

✅ 破法

关键洞察：state 的取值序列是确定的。 用动态 Trace 记录每次 switch 分发时 state 的值， 就能还原出真实的执行路径（下一节 Stalker 就是干这个的）。 工具层面，D-810 这类 IDA 插件就是自动化做这件事。

③ 虚假控制流（Bogus Control Flow，-bcf）—— 插入永不执行的分支

做了什么：在真实代码前后插入不透明谓词 （Opaque Predicate）——一种结果恒定、但静态看不出来的条件。 看起来程序有两条路，实际上永远走同一条。

// 插入的不透明谓词：这个条件永远为真，但 IDA 看不出来
if (((x * x) & 1) == ((x * x) % 2)) {   // 恒真：平方的奇偶性
    // 真实代码在这里
    if (x == 0x1234) return 1;
} else {
    // 死代码：一堆垃圾运算，永远不执行
    int junk = 0;
    for (int i = 0; i < 1000; i++) junk += i * i;
    return junk;
}
⚠️ 为什么它这么烦人

它不改变程序语义，只是让控制流图变复杂。 大量虚假分支会让 IDA 的反编译超时、让分析者浪费时间去判断哪个分支是活的。 更狠的版本会把一个函数拆成十几个互相跳转的碎片。

✅ 破法

动态执行时，死代码根本不会出现在 trace 里。 所以"跑一遍看真实路径"是最高效的破法。这也是本课的核心方法论： 静观看不懂的，就让程序自己告诉你。

④ 指令替换（Instruction Substitution，-sub）—— 用等价复杂指令迷惑反编译

做了什么：把简单指令替换成语义等价但形式复杂的指令序列。

; 混淆前
ADD  R0, R1, R2          ; R0 = R1 + R2  —— 一眼看懂

; 混淆后（等价变形）
SUB  R0, R1, R2
MVN  R3, R2              ; R3 = ~R2
ADD  R0, R0, #1
EOR  R0, R0, R3
EOR  R0, R0, R3          ; 绕了一圈还是 R1+R2

它偏爱用在常量比较上。比如 if (x == 0x1234) 会被拆成 一堆位运算组合，让你看不出那个魔数 0x1234 在哪。

✅ 破法

这类混淆对动态执行毫无影响——CPU 算出来的值是一样的。 所以在 Trace 里看寄存器最终的值，而不是看指令本身。 算法还原时我们关心的正是"这一轮算出什么"，而不是"它怎么算的"。

15.5Stalker：让程序自己把路走一遍给你看

上面四个"破法"都指向同一件事：动态 Trace。 Frida 里做这件事的引擎叫 Stalker。

直觉模型 · 行车记录仪

静态分析像看地图——能看到所有道路，但不知道司机实际走了哪条。
Stalker 像行车记录仪——它不关心地图上有没有岔路，只记录车轮实际碾过的每一米。

对于 OLLVM 混淆的代码，"地图"（控制流图）已经被搅成一团乱麻， 但"实际路线"永远只有一条，而且那条路上跑的就是真实算法。

Stalker 的三种追踪模式

API粒度能看到什么性能
Stalker.follow(threadId, {events:{call:true}}) 函数级 调用了哪些函数（call 事件） 较好
Stalker.follow(id, {transform}) 基本块级 每个基本块的地址、指令数 中等
Stalker.follow(id, {transform}) + iterator 指令级 每一条指令、寄存器读写、内存读写 很慢（10-100x）
🔥 性能警告

指令级 Trace 会让程序慢十倍到上百倍。 直接对一个 App 全程开指令级 Trace，结果通常是：程序卡死、ANR、或者被反调试检测到超时。
正确做法：先用静态分析定位可疑函数，只对那一个函数开 Stalker （用 transform 里的 iterator.putCallout 加范围判断）， 或者用 Stalker.exclude() 把无关模块排除掉。

🔑 加密算法的三个"落脚点"

无论算法怎么魔改，它总要在某个时刻碰到这三样东西——这就是你的钩子位置：

  1. 输入：明文从哪来（读内存的位置）
  2. 常量表 / 轮常量：S 盒、K 常量、初始向量——魔改也改不掉这一坨数据的结构
  3. 输出：密文写到哪去（写内存的位置）

15.8本章名词表

DBI
Dynamic Binary Instrumentation，动态二进制插桩。在程序运行时插入代码以观测/修改其行为。Frida 是最流行的移动端 DBI 框架。
ART
Android Runtime，Android 5.0 起取代 Dalvik。把 dex 字节码 AOT/JIT 编译为机器码，同时保留 Java 反射能力。
JNIEnv
JNI 环境指针，是 Native 代码调用 Java 层的唯一入口。每个线程一份，通过 JavaVM 获取。
Inline Hook
在目标函数入口写入跳转指令劫持执行流。需要可写内存权限与指令重定位能力。
PLT / GOT
Procedure Linkage Table / Global Offset Table。外部函数调用的跳转表，Hook 导入函数（如 strcmp）时常改这里。
不透明谓词
Opaque Predicate。结果恒定但静态难以判定的条件表达式，是虚假控制流的核心构件。
基本块
Basic Block。一段只有一个入口一个出口、内部无分支的指令序列。控制流分析与 Trace 的基本单位。
魔数 / 常量表
算法中固定的特征数据，如 MD5 的初始值、AES 的 S 盒。算法还原的主要突破口。
overload
Frida 中用于在方法重载时指定具体签名的方法。省略它会因歧义报错。
retval.replace()
唯一能修改 Native 函数返回值的方式。直接赋值 retval 无效。
