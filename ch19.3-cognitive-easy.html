控制流平坦化,一节学不会就分两次

生活类比 / 放松阅读 技术事实(要记) 操作步骤(按顺序做) 坑 / 不要这样想

这份讲义只讲 OLLVM 控制流平坦化这一件事,什么都不引入。如果读到一半脑子开始糊, 就关掉去喝水,第二天从"进度条"上你看过的最后一块接着看。
不需要一次看懂。看懂 60% 就已经足够你接下来去用其他工具。

块 1 / 8 · 一件必须先知道的事

①它没动你的代码,它动的是图纸

类比装修队里混进一个恶作剧设计师

编译 C/C++ 成安卓能跑的程序,过程像"装修一栋房子":

· 量房出图纸的师傅(叫做"前端")—— 把源码变成一张图纸
· 设计师(叫做"中端")—— 在图纸上反复改,优化、改动
· 施工的工人(叫做"后端")—— 按图纸造出真实机器码

OLLVM 就是混进设计师群里的一个恶作剧——他不换材料、不改房间数, 就是把图纸上的走廊全画成迷宫。

完工后房子住起来一模一样(程序跑起来行为不变),但拿到图纸的工人看得一脸懵—— 这就是为什么你拿 IDA 反编译会看到一坨像迷宫一样的 switch。

一句话建立坐标: OLLVM 在"图纸"那一层动手,不动你的源码,也不在最终机器码层动手。 你看到的迷宫,在图纸阶段就被定型了。
块 2 / 8 · 老实的代码长什么样

②先看一份"老老实实"的代码

类比一间房子的正常户型图

下面是混淆前的代码(伪代码,不必会写):

int 老老实实(int x) {
    int r = 0;
    if (x & 1) {           // ← 如果 x 是奇数
        r = x * 3;
    } else {              // ← 否则
        r = x / 2;
    }
    return r;
}

这段代码的流程图(阅读顺序)是:

开始
  │
  ▼
判断 x&1(奇/偶)
  │
  ├── 真 ──▶ 算 x*3 ──┐
  │                    │
  └── 假 ──▶ 算 x/2 ──┤
                       │
                       ▼
                      返回 r

人眼一秒钟就能看出来:进去、判断、走两条路中的一条、出门。这就是"好理解的代码"。

技术词(混个脸熟就行):
· 这张图就叫 CFG(控制流图);
· 每一个方框就叫一个 基本块。
后面我们反复用这两个词。
块 3 / 8 · OLLVM 想搞成什么样

③OLLVM 的目标:让流程图变怪

类比把户型图重画,但房间数量不变

OLLVM 想把刚才那种"清晰的两条路",改造成一个怪物:

改造前(图 ②):一条主干 + 一个分叉 → 两条小岔路。

改造后:

       ┌─────────────────────┐
       ▼                     │
    [ 分诊机器 ] ◀──────────┐ │
       │                   │ │
       ▼                   │ │
     算 x*3  ─────────┐     │ │
                      │     │ │
                      ▼     │ │
                写"下一步" ─┘ │
                      │       │
                      └──────┘

变成了一团:中间有个分诊机器在不停转,每块工作做完了都"回去"报告下一站。

看上去很乱对吧?但房间数没变。还是刚才那几个工作: "判断 x 奇偶"、"算 x*3"、"算 x/2"、"返回"。 OLLVM 没给你加任何新功能,只是把它们怎么互相跳转这件事搞得面目全非。
记住一句话:OLLVM 控制流平坦化 = 用一台"分诊机器 + 一个计数器",把"分叉走路"换成"绕圈查表"。
块 4 / 8 · 操作第一步 · 给房间拍个照

④第一步:先把所有基本块收进来

类比装修队进场,先拍照存底

改造之前,工人先要把当前所有基本块记下来,顺序照原本摆的样子来。 后面的步骤都要查这张表,所以这步不做,后面全乱套。

for (BasicBlock &BB : 函数F) {
    origBB.push_back(&BB);  // 全收进来
}
①

做完以后是啥样?

列表 origBB 里躺着你函数所有基本块,顺序就是原本的顺序。 这就是接下来一切动作的"底盘"。

这步是只读,没动图纸,只是在内存里做了个备份。 后面 5 步才是真改。
块 5 / 8 · 操作二&三 · 搭出"分诊台"和"叫号屏"

⑤第二步 + 第三步:分诊机器 + 计数器

类比医院入口设一台分诊台,挂一个叫号屏

现在动工。我们要在函数最前面塞一块新的基本块,叫它 分诊台;
然后在它里面,准备一张叫号屏(其实就是个小计数器),叫它 switchVar。

②

塞一个叫"disp"的新基本块,放到函数入口的前面

BasicBlock *disp = BasicBlock::Create(
    F.getContext(), "disp", &F, &F.getEntryBlock());
//                           ^^^^^^^^ 最后这个参数是"插在谁之前"
//                           插到了入口块前面 → 它成了全函数的"总枢纽"
③

放一个小计数器,叫 switchVar(初始值还没设)

IRBuilder<> B(&F.getEntryBlock());
Value *switchVar = B.CreateAlloca(Int32Ty);
// 它只是个普通的栈上变量,功能上却是"全函数的唯一真相":
//   下一步去哪儿,全看它当前值。
不要被"switchVar"三个字吓到。它就是个普通的整数变量, 初值不重要,后面那条 switch 指令会让它有意义的。
对应到 IDA 里你看到啥?
· disp 这个块 → IDA 那个巨大的 switch 语句;
· switchVar → IDA 那个switch 括号里的变量。
反混淆的核心,就是要追这一个变量的值变化。
块 6 / 8 · 操作四&五 · 装好叫号台,给每个房间发号码牌

⑥第四步 + 第五步:建 switch,每个基本块办张号码牌

类比挂号时给每个人发一张小牌子

分诊台有了,接下来:

· 在分诊台里装一台 "看号码叫人"的机器(C++ 这边叫 switch 指令);
· 给刚才备份的每个基本块,按拍照存底时的顺序,办一张号码牌。

办完以后,原来的"判断→走两条路"就消失了,变成了一张"号码 → 工作"的对应表。

④

在 disp 里装"看号码叫人"的 switch 指令

SwitchInst *sw = SwitchInst::Create(
    switchVar, disp, 0, disp);
//              ^^^^ ^^^^^^^ 默认目标也指向 disp
//              ↓
//            在 case 填好之前,这是个"空转死循环"
⑤

给每个备份里的基本块发号码牌

for (unsigned i = 0; i < origBB.size(); i++) {
    sw->addCase(ConstantInt::get(Int32Ty, i), origBB[i]);
}
// 即:块 0 = case 0、块 1 = case 1……
这一步做完,"原来的 if/while 关系就死了。 只剩"号码 → 块"的对应表。所有"接下来去哪儿"的信息, 都被 OLLVM 从跳转指令里抠出来,挪到了计数器变量里。 这是 IDA 看到一坨 switch 的根本原因。
块 7 / 8 · 操作六 · 在走廊中间塞一台状态写入器

⑦第六步(最关键的一刀):每条走廊中间塞个序言块

类比每条走廊中点装一台刷卡器,刷完告诉你下一步去哪

现在房子布局是这样:大家都得绕回 分诊台,分诊台才能告诉你下一站。 但屋里原来那些"走廊"还是老样子——每条走廊的尾巴,还连着原本的房间。

OLLVM 的最后一步:把每条走廊拦腰切断,塞一台"小机器",只做两件事:

⑥

把每条原始边切成两段,中间塞"序言块"

for (每条原始边 from → to) {
    BasicBlock *pro = SplitEdge(from, to);
    new StoreInst(nextState, switchVar, pro);
    //                       ↑ 把"下一站"写进计数器
    //                                    ↑ 这个序言块最终跳回 disp
}

塞好之后,格局变成下面这样:

     ┌───────────┐
     │   disp    │ <── 全函数唯一公共枢纽
     │  switch   │
     └─────┬─────┘
           │
     ┌─────┼─────┐─────┐─────┐
     ▼     ▼     ▼     ▼     ▼
   case0 case1 case2 case3 case4  ← 原本那些基本块(顺序与拍照时一致)
     │     │     │     │     │
     ▼     ▼     ▼     ▼     ▼
  [序言块][序言块][序言块][序言块][序言块]  ← 新插入的小机器
     │     │     │     │     │
     └─────┴─────┴─────┴─────┘
                  │
                  ▼
              写"下一状态" → 跳回 disp
记住:每个序言块 = 写一次 switchVar + 跳回 disp。这就是 IDA 反编译出的 switch{} case{} break; 结构的来源。
块 8 / 8 · 跑一遍看看 · 给大脑最后一个画面

⑧我们跟着计数器走一遭,看它怎么用

假设 x = 5(奇数),我们想看 x*3 = 15 这条路径会发生什么。

① 进入 disp
   switchVar 还是 0
   ↓
② switch(0) → 跳到 case 0(就当它是初始化块)开始
   ↓
③ case 0 做完,走到它末尾的"序言块"
   序言块:switchVar = 1 → 跳回 disp
   ↓
④ 回到 disp
   switch(1) → 跳到 case 1(假设 case 1 是"判断奇偶"块)
   ↓
⑤ case 1 判断 x&1 = 1(奇数),走到末尾的"序言块"
   序言块:switchVar = 2(因为奇数要算 x*3)→ 跳回 disp
   ↓
⑥ 回到 disp
   switch(2) → 跳到 case 2("算 x*3"块)
   ↓
⑦ case 2 把结果 r = 15 算出来,走到末尾"序言块"
   序言块:switchVar = 4(代表"返回"块)→ 跳回 disp
   ↓
⑧ 回到 disp
   switch(4) → 跳到 case 4("返回"块),函数结束

看到了吗?程序实际做的事情没变,但它不再"顺序往下走", 而是"每做一步就回到分诊台请它再叫我下一站"。

反混淆的关键就是追 switchVar。
· 在 IDA 里,这个变量是 switch 圆括号里的那个名字;
· 它每变一次值,就说明程序"准备去下一个 case";
· 把每次"变到什么值"连起来,你就拿到了真实的执行路径。
这就是为什么反混淆的核心做法是"动态 Trace",而不是"静态读 switch"。
OLLVM 控制流平坦化做的全部事,就两件:① 设一台分诊台 ② 在每条走廊中点装一台"刷写下一站"的小机器。其余一切都是这两件事的自然结果。
