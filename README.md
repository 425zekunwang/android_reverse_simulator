把 **32 章**安卓逆向课程内容，重做成一套**可交互的网页模拟器**。
不是讲义，是一台能动手操作的机器。

## 设计理念

每章的结构是固定的四段式，对应**认知建立的四个阶段**：

| 阶段 | 手段 | 组件 | 解决的问题 |
|---|---|---|---|
| ① 建立直觉 | 生活类比 | `intuition` 直觉模型卡 | "这东西到底是什么？" |
| ② 看清机制 | 可视化 + 逐步执行 | `stepper` 代码步进器、`stage` 动画舞台、`term` 终端模拟 | "它内部怎么运作？" |
| ③ **动手验证** | **自己算一遍** | **`lab` 交互实验室**（真实算法库驱动） | "我能自己算出来吗？" |
| ④ 学会决策 | 情境演练 | `decision` 决策树 | "真实工程里我该怎么选？" |
| ⑤ 验证理解 | 追问 + 自测 | `teacher` 苏格拉底严师、`quiz` 测验 | "我是真懂了还是看过了？" |
| ⑥ **对接实战** | **真实案例拆解** | **`case` 实战案例**（索引到可验证来源） | "别人真这么干过吗？" |
| ⑦ 整体回顾 | 演示稿 | `deck` PPT 幻灯片（`slides.html`，75 页） | "能不能串起来讲一遍？" |

**`lab`（交互实验室）与前几类组件的根本区别：读者要动手算，不是看动画。**

### 📁 实战案例（`case` 组件 + `cases.html` 索引页）

课程内容之外，另有从社区采集的**真实逆向案例**，每条都：
① 有可验证的原始 URL；② 用本章的方法论重新拆解；③ 如实保留原作者自述的局限。

**采集原则**：

- **只收录实际抓取到内容、且有可验证 URL 的案例。** 抓取失败的如实标注，不硬凑。
- **不确定的地方标注为「待核实」**，与正文同一标准。原作者自己标为不确定的，我们照样标注，不代其下结论。
- **重点保留「局限与未完成」**。公开案例往往只讲成功路径，但真正的经验藏在"哪里没做成、为什么"。

**当前收录 42 条案例**（27 条看雪 + 15 条 GitHub），覆盖全部 32 章。

> **采集方法备忘**（均为本站实测，供后续扩充时参考）：
> - **看雪正文在一个 `<textarea class="js-message-markdown">` 里，不在可见 DOM 中。**
>   很多抓取工具只能拿到"登录后可查看完整内容"这层外壳。**判断正文是否可读，要看这个 textarea 的字节数**
>   （几百字节以上才算正文，只有 7020 字节且 title 是"安全验证"的是验证墙）。
> - **验证墙不是全站行为，是逐帖命中的。** 实测同一批链接里，有的能取到完整正文（如 74079 / 38038 / 27503 字节），
>   有的只有验证页。**所以必须逐帖验证，不能凭站点印象下结论。**
> - **看雪的 `article-NNNNN.htm` 路由不稳定**：实测会出现 404（22 字节），而同一时刻 `thread-NNNNN-1.htm` 正常。
>   **引用时用 `thread-` 路由**；第 9 章那条历史遗留的 `article-` 链接已在案例里写明访问说明与搜索兜底。
> - **用 Node 的 `fetch` 验证，不要用 PowerShell 的 `Invoke-WebRequest` 或 `curl`**——
>   本机这两个走不通 TLS（返回 000 / SSL 错误），会白白浪费时间。
> - `52pojie.cn` 多数帖子返回 200 但正文为空（需登录），基本不可用。
> - **GitHub 是最可靠的来源**：仓库页 + `raw.githubusercontent.com/.../README.md` 稳定可用。
>   注意老仓库的分支名可能是 `master` 而不是 `main`。

**第 15–32 章（进阶与深水区，19 个实验）**

**这些计算不是写死的字符串**，而是真实实现：`assets/labs.js` 提供 MD5、SHA-1、CRC32、Adler-32、
Base64、RC4、HMAC-MD5、AES-128/192/256（用公开测试向量 RFC 1321 / RFC 2202 / RFC 4648 / FIPS-197 / FIPS-180 校验过）；
新增章节的实验同样如此——第 14 章的 DFA 推演器真的加密两次并解方程，
第 6 章的 RSA 实验真做模幂与扩展欧几里得，第 7 章真用 S 盒逐字节比对。

**其中「严师」是本项目的核心创新。** 它不是选择题——它要求你用**自己的话**把关键概念说全。
系统会按语义匹配检查你命中了哪些要点，没说过关就**逐轮追问**（最多 3 轮），
每轮给出更具体的提示与更尖锐的追问。

**第三次仍不过关时，它会给出参考答案——但这一题不会就此结束**，而是被标记为「待复述」：
你必须关掉答案、凭记忆重写一遍。系统会用字符 bigram 相似度比对，
**与参考答案重合度超过 72% 会被判定为抄袭并打回**。只有用自己的话复述、且命中要点，才算真正过关。

> 这条设计对应一个朴素的判断：**能在多个选项里认出正确答案（辨认），和能凭空重建它（回忆），是两种完全不同的掌握程度。**
> 严师只认后者。

## 技术架构

```
assets/style.css            设计系统（深色工程风）
assets/app.js               运行时：导航 / 进度 / 9 个交互组件 / 苏格拉底引擎 / COURSE 元数据
assets/chapter.js           章节渲染器：把数据渲染成页面
assets/labs.js              算法库：MD5/SHA-1/CRC32/Base64/RC4/HMAC/AES 的真实实现
assets/labx.js              实验工具：十六进制比对、算法指纹识别、C 数组解析、syscall 表等
chapters/chNN.js            章节内容（数据文件，window.CHAPTER = {...}）
chNN-*.html                 章节外壳（~570 字节，只负责加载上面几个脚本）
validate-chapters.mjs       全站结构与运行时校验器（见下）
build-cases.mjs             从各章数据文件生成 cases.html
check-integrity.mjs         一致性检查：每章内容标题必须与 COURSE 元数据对得上
CHAPTER-SPEC.md             新章节写作规范（新增章节时的唯一契约）
```

**关于章节编号：** `COURSE.chapters[i].no` 与 `file`、`chapters/chNN.js` 的文件名、
以及每章数据里的 `no` / 小节号 `h`（如 `'3.2'`）必须始终一致——
`validate-chapters.mjs` 会逐条对账，因此**改章号必须整套一起改**，不能只改其中一个。

> 最初的 18 章在 `COURSE` 里带 `legacy: true` 标记，用于区分"已验收的历史内容"与"后补章节"：
> 只有后补章节才受 `validate-chapters.mjs` 的「新章组件密度下限」约束。
> **注意这个判定不能用章号写死**——章号已按学习顺序重排，历史 18 章现在是第 15–32 章。

**为什么章节内容是数据文件而不是 HTML？**
因为这样可以用极小的工作量保证 32 章的一致性——页面骨架、组件装配、导航、进度统计全部由
`chapter.js` 统一生成，章节作者只需提供内容数据。

### 组件 API 速查

```js
window.CHAPTER = {
  no: 1, title: '标题', lede: '导语', meta: ['核心问题：<b>…</b>'],
  sections: [{
    h: '1.1', title: '小节标题',
    html: '<p>正文</p>',
    intuition: { tag: '直觉模型 · XXX', body: '<p>类比</p>' },
    stepper:   { title, lines: [{ code, note, state, mem }] },
    stage:     { title, render, reset, steps: [{ run, note }] },
    term:      { title, lines: [{ t: 'p|o|e|w|d', s, note }] },
    decision:  { start, nodes: { n0: { scenario, choices }, … } },
    lab:       { title, inputs, run, expected, showAnswer, hint },
    case:      { source, title, link, … },
    quiz:      { id, chapter, answer, stem, options, explain }
  }],
  glossary: [{ t, d }],
  teacher: { id, chapter, questions: [{ id, depth, q, concepts, hints, probes, model }] }
};
```

内置 `T` 助手简化常见结构：`T.note(kind,title,body)`、`T.tbl(head,rows)`、
`T.card()`、`T.acc()`、`T.term()`、`T.code()`、`T.grid()`、`T.pill()`。
动画里用 `S(id,cls)` 设方块状态、`CLS(id,cls)` 设任意元素类名、`SET(id,html)` 设内容。

## 工具脚本

```bash
node validate-chapters.mjs            # 全站校验（32 章）
node validate-chapters.mjs 1 2        # 只校验指定章节
node validate-chapters.mjs --quiet    # 只输出问题

node build-cases.mjs                  # 从各章数据文件重新生成 cases.html
node build-cases.mjs --check          # 只检查 cases.html 是否已过期（不写文件）

node check-integrity.mjs              # 一致性检查：章号 / 标题 / 文件名 三者对账
node verify-only-renumber.mjs         # 内容保真审计：比对新旧数据，只允许编号不同
```

**`build-cases.mjs`** 把散在 31 个章节数据文件里的 `case` 组件抽出来，按来源分组成 `cases.html`。
案例索引必须自动生成——手工维护一个 42 条的索引页，必然和正文不同步。
（第 15 章是早期内联格式，它那条案例在脚本里手工登记并标注，因为无法自动抽取。）

**`validate-chapters.mjs`** 是这个仓库里**唯一**的结构校验工具，它做八件事：

1. **元数据一致性**——章节编号连续、track 有定义、外壳 HTML 的 `data-chapter` 与 COURSE 对得上。
2. **重复键扫描**——行级 + 花括号深度跟踪，抓出 `{a:1, a:2}` 这种被 JS 静默覆盖的键。
   （章节文件是手写的两百多 KB 数据，重复键不会报错，只会少渲染一块。）
3. **结构校验**——小节编号连续、decision 图从 start 可达且每个 choice 的 next 存在、
   quiz 的 answer 不越界、lab 的 input key 不重复、teacher 的每个 concept 都有匹配词。
4. **真实执行 Lab 与动画**——用输入框的预填值真的调一遍 `lab.run` / `lab.expected` /
   `stage.reset` / 每个 `stage.steps[].run`，抓抛异常与非字符串返回。
5. **动画 id 一致性**——从 `render` 抽 id，从 `reset`/`run` 的**函数源码**抽被引用的 id 并对账。
   为什么必须查：`S('不存在的id')` 是**静默无操作**，浏览器不报错、控制台干净，动画就是不动。
   形如 `S('row-' + i, …)` 的动态 id 会退一步核对"前缀是否出现在 render 里"。
6. **CSS 类名存在性**——抽出章节数据里用到的 class，逐个核对 `assets/style.css` 里有没有定义。
7. **渲染 + 装配冒烟测试**——把整章真的交给 `renderChapter` + `mountAll`，

## 已知限制

1. **第 15 章是早期格式**（内联脚本，100 KB），其余 31 章是数据文件格式。功能一致，仅实现方式不同。
2. **进度存储在 localStorage**，清除浏览器数据会丢失；首页提供"导出进度"功能。
3. **`file://` 协议下 localStorage 在部分浏览器受限**，此时进度仅保存在内存中（当次会话有效）。
   如需持久化，可用 `python -m http.server` 起个本地服务器。
4. **体积较大**（全站 ~6.2 MB，单章 200–300 KB）。纯静态、无构建的场景下不影响使用，
   但首屏加载单个章节需要解析两百多 KB 的 JS。
5. **环境配置类章节（第 5 章）的具体命令与参数最容易过期**——正文只给"形状"不给参数，
   凡涉及版本的地方均标注待核实。
6. **eBPF 章节（第 25 章）的安卓现状**基于 2023 年前后信息，实际支持情况因设备与内核版本差异极大。
7. **白盒密码（第 14 章）与 AI 辅助（第 7 章）的部分结论依赖外部论文与当期生态**，
   本站只讲机制、不对具体构造的攻破复杂度或工具能力下断言。
8. **AI 辅助章节（第 7 章）标了 26 处待核实**——这是全站最高的一章，因为那个领域半年就会变一轮。
